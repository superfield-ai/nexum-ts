## Claim

PostgreSQL with pgvector is sufficient for corpora below 20M blocks with mixed document types, with no measurable query quality degradation vs. a specialized graph DB.

## Operationalization

Dataset: synthetic corpus at 1M, 5M, 20M blocks across 3 domain mixes (legal, medical, mixed).
Metric: query latency P50/P99 (ms) for semantic, full-text, and 4-hop graph traversal queries.
Baseline: same queries on Kuzu with identical block/link data.
Intervention: pgvector HNSW + recursive CTE vs. Kuzu native graph engine.
Acceptance criterion: P99 latency delta < 2x at 20M blocks for all three query modes.

## Null Hypothesis

PostgreSQL degrades past 2x P99 latency vs. Kuzu at or below 20M blocks, indicating a dedicated graph DB is required at legal-corpus scale.

## Experiment Spec

1. Generate synthetic corpus: 1M / 5M / 20M blocks with random 1536-dim embeddings and link graphs at average degree 5.
2. Load into PostgreSQL 16 with pgvector HNSW index and GIN tsvector index.
3. Load same data into Kuzu.
4. Run 1000 queries per mode (semantic ANN k=20, full-text, 4-hop graph traversal) against each DB.
5. Record P50/P99 latency per query mode per scale.
6. Compare.

## Results

### G1-OPT-1 (issue #73, PR #81) — partial result

Status: **latency target met; recall floor pending (synthetic-data caveat)**.

**Setup**

- pgvector 0.8.2 on PostgreSQL 16.13 (Docker, `pgvector/pgvector:pg16`).
- 1 000 000 blocks × 384-dim float32 embeddings (random Gaussian unit vectors, ingested by PR #72).
- HNSW index `blocks_embedding_hnsw_idx`, `m = 16`, `ef_construction = 64`.
- Container: `shared_buffers = 1 GB`, `maintenance_work_mem = 2 GB`, `--shm-size=2g`.
- Index size: 1 953 MB (exceeds `shared_buffers` — cold cache shows
  `Buffers: shared hit=95 read=776` per query but query is still ~5 ms).

**ef_search sweep (m=16 float32, n=100 corpus-sampled queries)**

| ef_search | P50 (ms) | P99 (ms) | recall@10 |
|---|---|---|---|
| 20  | 8.4  | 12.3 | 0.063 |
| 40  | 11.1 | 17.8 | 0.107 |
| 80  | 19.5 | 27.5 | 0.143 |
| 200 | 37.5 | 52.2 | 0.190 |

**Root cause of PR #72's P99 = 2424 ms**

Not memory pressure, not Docker I/O, and not a bad HNSW parameter
choice. PR #72's benchmark was running against an un-indexed table:
the schema loader (`experiments/g1-postgres-scale/schema.py`) silently
dropped any multi-line SQL statement whose first line was a `--`
comment, including the `CREATE INDEX … USING hnsw …` block. Every
ANN query degraded to a parallel sequential scan over 1 M × 384-dim
vectors (~3.0 s in EXPLAIN ANALYZE).

The fix (PR #81) is a two-line change in the schema-statement loop
plus a defensive post-apply assertion that
`blocks_embedding_hnsw_idx` exists. With the index present the
binding constraint disappears: P99 = 17.8 ms at the default
`ef_search = 40`, **28× under the 500 ms gate criterion** and 11×
under the 200 ms G1-OPT-1 stretch target.

**Caveat — recall@10 is unmeasured at this gate**

The 6–19 % recall@10 figures above are **not** an index quality
signal. PR #72 ingested random Gaussian vectors as embeddings, so
"true top-10 nearest neighbours" is statistical noise — there is no
semantic structure for HNSW to recover. recall@10 at this scale with
random unit vectors is bounded near 10/√N regardless of index
parameters. The H1.1 acceptance criterion (recall@10 ≥ 0.90) cannot
be evaluated here and is deferred to **G1-OPT-2**, which must ingest
real model embeddings (`all-MiniLM-L6-v2`) before re-running the
sweep.

**Verdict for H1.1 at the G1-OPT-1 milestone**

PostgreSQL with a correctly-built HNSW index meets the 500 ms P99
gate at 1 M blocks **with substantial headroom** (28× margin), with
no measurable need to switch to a dedicated graph DB on the latency
axis. The 5 M and 20 M scale points — and the recall comparison vs.
Kuzu — remain to be measured under H1.1's parent experiment.

### G1-OPT-2 (issue #74, PR #82) — diagnosis & fix candidates

The diagnosis harness lives at
`experiments/g1-postgres-scale/traversal_diagnostics.py` and implements
the issue #74 protocol:

1. **Step 1 — `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`** on the
   recursive CTE; extracts the index used on the recursive join, the
   set of seq scans on `links`, total `Heap Fetches`, total
   `Shared Read Blocks`, and the planner's row estimate vs. actuals.
2. **Step 2 — fan-out per hop:** raw row count vs.
   `count(distinct id)` per depth, aggregated across many seeds.
   Quantifies whether the cycle guard is actually shrinking the
   frontier or whether fan-out is exponential.
3. **Step 3 — cycle-guard ablation:** baseline vs. the same query
   without `l.src != ALL(t.path)`. A large speed-up implicates the
   array-containment check as the bottleneck.
4. **Fix benchmarks** (each returns per-hop P50/P99):
   - **Fix A** — covering index
     `links_src_layer_cover_idx (src, layer) INCLUDE (dst, rel_type, weight)`
   - **Fix B** — `SET work_mem = '256MB'` for the session
   - **Fix C** — top-k highest-weight outgoing edges per
     `(src, layer)` (recall trade-off — recall loss measured separately)
   - **Fix D** — application-side BFS with
     `WHERE src = ANY($frontier)` (no recursive plan, bounded memory)

`traversal_diagnostics.run_full_diagnosis` is the orchestration entry
point and returns a single envelope with all four fix benchmarks plus
`chosen_fix`. The selector prefers A → B → D → C: pick the cheapest
semantic-preserving fix that meets the 500 ms P99 gate threshold;
fall back to the recall-trading top-k fix only if nothing else works.

If A–D all miss the 500 ms P99 bar, issue #74's acceptance criteria
require hard-capping the production API at 4 hops in
`src/routes/query.ts` (with a 400 error for greater values) and
re-confirming 4-hop P99 < 200 ms at 5M blocks. Apache AGE / pgrouting
remain Postgres-only fallbacks but are intentionally NOT implemented
in this module; pursue only if A–D fail.

Live measurements against the 1M / 5M corpora are pending an
environment with Postgres 16 plus the ingested fixture; the harness is
ready to be invoked from `run_benchmark.py` once such an environment is
available.
